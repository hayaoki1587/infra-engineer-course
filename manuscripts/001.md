# 第1講 システム基盤とは何か ― インフラエンジニアの役割と担当範囲

## 到達目標
システム基盤の範囲を説明し、利用者の操作が各層を通過する仕組みを追い、障害時の一次切り分けと担当間連携を説明できる。

## 資料と位置づけ
基準：本講座「運用マスター v1.1」「curriculum.json」（2026-11-21確認）。外部の公式製品マニュアルは本講で未照合。以下のWeb/AP/DB構成、コマンド、ログは一般的な仕組みを説明するための架空の検証例であり、特定製品の稼働保証ではない。
重要度：A（必須）システム基盤・処理経路・担当範囲・障害切り分け、B（補助）運用の観測と連携、C（発展）責任分界と設計トレードオフ。

## 1. システム基盤が必要な理由
企業システムでは、画面が正しく作られていても、通信経路が切れれば利用できない。DBの容量が尽きれば登録できない。夜間バッチが動かなければ翌朝の帳票が古いままになる。業務機能を継続して届けるために、アプリケーションが動く土台と共通機能を整える必要がある。これが「システム基盤（ITインフラ）」である。
基盤は単なる物理サーバではない。計算資源、OS、ネットワーク、ストレージ、DBMS、Webサーバ、認証、監視、バックアップ、ジョブ管理、仮想化・クラウド、運用手順まで含む。企業ごとに担当境界は異なり、DBMSやWebサーバをアプリチームが管理する場合もある。

## 2. 業務機能と基盤機能
「商品を検索する」「注文を確定する」は業務機能。CPU・メモリを配分する、HTTPS通信を受け付ける、DBへの接続を維持する、障害を監視する、バックアップから復元するのは基盤側の機能である。ただし注文確定のSQLやAPI実装は通常アプリ側の責任であり、DBMS自体の起動・容量・性能管理はDB基盤担当となることが多い。境界は契約・組織・設計書で決めるので、製品名だけで断定しない。

## 3. 例：3層システムの正常な処理
架空の社内タスク管理システムを考える。利用者のブラウザからWeb層（Nginx）、AP層（FastAPI）、DB層（PostgreSQL）へ処理が流れる。これは理解用の一例であり、全システムが3台の物理サーバに分かれるわけではない。各層はコンテナや仮想マシンで動いてもよい。

1. 利用者が「一覧表示」を押す。ブラウザはURLの宛先を名前解決し、ネットワークを通じてWeb層にHTTP(S)リクエストを送る。
2. Web層は静的コンテンツを返すか、/api/tasks のようなAPI要求をAP層に転送する。Web層は転送先のアドレス・ポートを設定で知る。
3. AP層は入力と認証・権限を確認し、必要なデータを得るためDB接続を利用してSQLを発行する。
4. DBMSは必要なデータをストレージから読み、キャッシュも活用しながら結果を返す。書き込みならトランザクションと永続化の仕組みが重要になる。
5. AP層が結果をJSON等に整形し、Web層経由でブラウザへ返す。ブラウザは画面を描画する。

この経路では、Web層の稼働だけでは「業務が正常」とは言えない。Web→AP、AP→DB、DB内部の処理まで成功して初めて一覧が表示できる。

## 4. 基盤担当者の仕事を時系列で見る
企画・要件定義では「何人が同時利用するか」「何分停止できるか」「どの情報を保護するか」を確認する。設計ではサーバの台数・CPU・メモリ、ネットワーク分離、冗長化、監視項目、バックアップ方式を選ぶ。構築ではOSやミドルウェアを導入し、設定値を記録する。テストでは正常系だけでなくAP停止、DB停止、ディスク逼迫、ネットワーク断などの異常系も試す。運用では監視、容量管理、パッチ、バックアップ確認、変更管理、障害対応を継続する。移行ではデータ整合性、停止時間、切り戻し手順を用意する。
運用保守は「決まった手順を押すだけ」ではない。ジョブ失敗の原因をログから説明し、復旧の影響を判断し、再発防止の設計変更を提案するところまで含む。

## 5. 何を観測するか：状態・ログ・設定
状態（今どうなっているか）、ログ（いつ何が起きたか）、設定（どう動くはずか）を突き合わせる。たとえばLinuxの検証環境では `systemctl status nginx` でサービス状態を、`journalctl -u nginx --since "10 minutes ago"` でsystemd管理下のログを確認できる。ただしコンテナ運用やログ転送方式によって確認場所は異なる。HTTP疎通の例として `curl -i http://127.0.0.1:8080/api/health` がある。これは自分の端末の8080番へ接続するため、Web層が別ホストにある場合はそのホストに合うURLに変更する。200は応答が返った一例で、業務機能の完全な正常性は保証しない。503はサービスが要求を処理できない状態を表すことがある。
ログの架空例：
```text
2026-11-21T09:00:01Z web request GET /api/tasks status=502
2026-11-21T09:00:01Z web upstream connect() failed target=ap:8000
2026-11-21T09:00:02Z ap service=stopped
```
この場合、Web層はリクエストを受け取っているが、AP層への接続に失敗している可能性が高い。502だけで「AP停止」と断定せず、APプロセス、接続先設定、名前解決、ネットワーク制御、ポート待受を確認する。時刻のタイムゾーンを合わせ、ログの前後関係を追うことが大切である。

## 6. 障害はどこで伝播するか
**Web停止**：入口が応答しない。ブラウザでは接続失敗やタイムアウトになり得る。Webプロセス、待受ポート、経路を確認する。
**AP停止**：Webは稼働していても転送先に接続できず、502/504などになり得る。Webの上流接続ログとAPのサービス状態を照合する。502/504の具体的な発生条件はプロキシ設定や失敗形態に依存する。
**DB停止**：APのDB接続が失敗し、APIが500/503等を返すことがある。APの接続エラー、DBサービス、DBへの経路を確認する。DB停止時に必ず503になるわけではない。
**ストレージ逼迫**：DBの書き込みが失敗し、登録処理だけ失敗することもある。ファイルシステム空き容量、DBログ、書き込みエラーを確認する。読み取り機能が一見正常でも安心できない。
このように「画面が見えない」という利用者の症状から、どの境界まで正常に通過したかを一段ずつ確認する。

## 7. 障害対応の実務手順
①影響範囲（全利用者か一部か、閲覧だけか更新もか）を確定する。②発生時刻と直前の変更を確認する。③入口から下流へ、または最後に正常だった地点から境界を絞る。④監視値・ログ・設定・疎通を照合する。⑤暫定復旧と恒久対策を分け、実施前にリスク・承認・切り戻しを確認する。⑥復旧後は業務動作まで検証し、時系列・根本原因・再発防止を記録する。
たとえばAP停止時に無条件で再起動するのは危険である。処理中のトランザクションや他系への切替、ジョブ実行状態を確認する。DB障害時も安易にデータファイルを削除しない。実際の本番変更は承認された手順に従う。

## 8. 設計判断：冗長化とバックアップは別物
Web/APを2台にしてロードバランサで分散すれば、単一ノード停止の影響を小さくできる。ただし共通DBが1台ならDBが単一障害点になる。さらに冗長化しても、誤削除したデータが両系へ反映される場合があるため、世代を保持したバックアップと復元訓練が必要になる。
単一構成は安価で単純だが停止リスクが高い。冗長構成は可用性を上げられる一方、費用、監視、切替試験、データ整合性管理が増える。設計では「停止許容時間」「データ損失許容量」「予算」を確認して選択する。

## 9. 実務製品との接続
Oracle DatabaseはDBMS基盤の例であり、インスタンス、データファイル、ログ、バックアップ・復旧を管理する。JP1/AJSは業務・運用ジョブの実行順序とスケジュールを管理する製品群の例であり、ジョブが正常終了しても業務データの妥当性は別途確認する。NetBackupはバックアップ運用の製品例、Citrixは仮想アプリ・デスクトップ配信の製品例である。製品固有の詳細動作は各専門講で公式仕様を照合する。

## 10. 要点
システム基盤はアプリを支える資源と共通機能、および継続運用の仕組みである。正常処理は利用者からWeb/AP/DBへ境界を越えて流れる。障害時は症状だけで犯人を決めず、状態・ログ・設定・通信を照合する。担当分界は組織で異なり、障害時には連携が必須。冗長化とバックアップは目的が異なる。
