# 第2講 企業情報システムの全体構成と主要コンポーネント

## 到達目標
企業情報システムの主要コンポーネントを「利用者・入口・業務処理・データ・共通サービス・運用」に分類し、正常な処理経路と障害時の依存関係を説明できる。構成図を読むときに、物理配置と論理的な役割を混同せず、障害範囲と設計上の単一障害点を指摘できる。

## 資料・適用範囲・重要度
2026-11-21に本講座の運用マスターv1.1、curriculum.json、progress.json、第1講原稿をGitHubから確認した。外部の公式製品仕様・参考書の該当章は本講では未照合。ここで示すホスト名、IPアドレス、ログ、設定、処理時刻は学習用の架空例であり、実在の組織や製品の既定値ではない。
A必須：構成要素・依存関係・正常処理・障害切り分け。B理解補助：共通サービスと運用観測。C発展：可用性と責任分界の設計判断。

## 1. 企業情報システムを一枚で捉える
企業の受発注システムを考える。利用者は社内端末または外部ブラウザから画面を操作する。リクエストはDNSなどの名前解決、ファイアウォールやロードバランサ、Webサーバ、APサーバを経由してDBに届く。処理結果は逆方向に返る。これとは別に、認証、時刻同期、監視、バックアップ、ジョブ管理などが各層を支える。
重要なのは「機器の一覧」と「処理の経路」を区別すること。構成図にサーバが10台あっても、注文登録の経路に直接関与するのは一部である。逆にDNSや認証が停止すると、多数の業務システムへ影響が及ぶことがある。

## 2. 主要コンポーネントの役割
**利用者端末・クライアント**：ブラウザや業務アプリを実行し、リクエストを送る。端末のネットワーク設定や証明書も利用可否に関係する。
**DNS**：ホスト名をIPアドレス等に解決する。DNSが障害でもキャッシュにより一部通信が継続する場合があり、全利用者が同時に失敗するとは限らない。
**ファイアウォール（FW）**：通信の送信元・宛先・ポート・状態などを条件に許可・拒否する。通信経路にFWが存在しても、許可設定がなければ通らない。
**ロードバランサ（LB）**：複数のWeb/APインスタンスへ要求を振り分け、ヘルスチェックにより異常な宛先を外す構成がある。ただしヘルスチェックの内容が浅いと業務障害を検知できない。
**Webサーバ／リバースプロキシ**：HTTP(S)を受け付け、静的ファイルの配信やAPへの転送を行う。
**APサーバ**：認証・入力検証・業務ルール・トランザクション制御などを実装し、DBや外部APIを利用する。
**DBMS**：データの検索・更新・同時実行制御・永続化を担う。DBサーバとストレージは同義ではない。
**ストレージ**：DBファイルやログなどを永続的に格納する。SAN、NAS、ローカルディスク、クラウドストレージなど方式は異なる。
**認証基盤**：利用者やサービスの本人性を確認し、権限情報を提供する。認証と認可は異なる。
**ジョブ管理**：日次締め、帳票、バックアップなどの処理順序・実行時刻・結果を管理する。ジョブの終了コード0は業務データの正しさを保証しない。
**監視・ログ基盤**：死活・性能・エラー・業務指標を収集し、異常を検知する。監視基盤の障害は必ずしも業務停止を意味しないが、障害発見を遅らせる。
**バックアップ基盤**：障害や誤操作からデータを復元するため、取得・世代管理・保管・復元確認を行う。冗長化の代わりにはならない。

## 3. 論理構成と物理構成を区別する
論理構成はWeb/AP/DB、認証、監視など「何を担当するか」の図。物理構成はどの物理サーバ、仮想マシン、コンテナ、ネットワーク、ストレージに配置されるかの図である。WebとAPが別コンテナでも同一物理ホスト上なら、そのホスト故障で両方停止する。逆に一つのDBサービスが複数ノードで構成される場合もある。
ネットワーク境界も論理的に区別する。外部公開ゾーン、AP内部ネットワーク、DB専用ネットワークを分離し、必要な通信のみ許可する。ゾーン分離は「絶対安全」を意味せず、運用・認証・更新も必要である。

## 4. 正常処理：注文登録の一連の流れ
架空の注文システムで、利用者が「注文確定」を押す。
1. 端末は注文サイトの名前をDNSで解決する。DNSキャッシュがあれば問い合わせを省く場合もある。
2. 端末はHTTPSで入口へ接続する。FWが通信を許可し、LBが正常と判断したWeb層へ振り分ける。
3. Web層はリクエストをAP層へ転送する。AP層は利用者の認証情報と注文内容を検証する。
4. AP層はDBへSQLを送り、在庫や注文レコードをトランザクションとして更新する。失敗時には整合性を保つためロールバック等が必要になる。
5. DBが処理結果を返し、AP層は成功応答をWeb層経由で利用者へ返す。
6. 監視は処理時間やエラー率を観測し、必要に応じてジョブ管理が後続の出荷連携処理を実行する。後続処理が非同期の場合、画面の成功と出荷完了は同義ではない。
この処理の途中で認証基盤やDBが使えなければ、Webサーバが稼働していても注文は失敗する。

## 5. 設定とログを結びつける
以下は検証環境での例。実機の設定・ログ形式は製品と導入方式によって異なる。
```text
# 架空の通信許可ルール（概念）
client -> lb:443       allow
lb -> web:8080         allow
web -> ap:8000         allow
ap -> db:5432          allow
client -> db:5432      deny
```
「client→dbを拒否」するのは、利用者がDBに直接アクセスせずAPの業務ロジックを経由するためである。DBへのアクセス経路を限定することは防御の一層になる。
```text
09:10:00 lb request_id=R42 upstream=web-2 status=200
09:10:00 web-2 request_id=R42 upstream=ap-1 status=200
09:10:00 ap-1 request_id=R42 db_query_ms=18 result=success
```
共通のrequest_idで処理を追うと、どの層まで到達したかが分かる。実運用では時計の同期、ログの保存先、機微情報のマスキングが必要。
Linux検証環境での読み取り専用確認例：
```bash
getent hosts example.internal
ss -lnt
curl -i --max-time 5 http://127.0.0.1:8080/api/health
df -h
```
`getent`は名前解決結果、`ss`は待受ソケット、`curl`は指定したHTTP入口、`df`はファイルシステム容量を確認する。環境にコマンドがない場合や、ローカルに対象サービスがない場合は失敗する。HTTP 200だけではDB書き込みや業務処理まで正常と断定できない。

## 6. 障害伝播：どこが止まると何が起きるか
**DNS障害**：新しい名前解決が失敗する可能性がある。IP直指定での疎通とDNS問い合わせを分けて調べる。ただしHTTPSの証明書や仮想ホストの都合で、IP直指定のブラウザ操作は業務確認として適切でない場合がある。
**LB障害**：LBが単一構成なら入口全体が止まる。バックエンドが健全でも利用者から届かない。
**Web障害**：対象Webインスタンスへの振り分けを停止できれば他系で継続可能な場合がある。全Web停止なら入口が失われる。
**AP障害**：Webは応答してもAPIが502/504等になる場合がある。接続先設定、AP待受、ネットワーク経路を確認する。
**DB障害**：参照・更新が失敗する可能性がある。APログ、DBログ、接続数、ストレージを確認する。DB障害が常にHTTP 503になるわけではない。
**認証基盤障害**：新規ログインが失敗しても既存セッションは継続することがある。キャッシュやトークンの有効期間に依存する。
**ジョブ管理障害**：オンライン注文が継続しても、夜間の集計や外部連携が遅れる可能性がある。
**監視障害**：業務自体は稼働していても異常の発見・通知が遅れる。監視対象と監視基盤の双方を観測する工夫が必要。

## 7. 実務ケース：画面は開くが注文できない
状況：トップページは表示される。注文確定を押すとエラー。直前にDBサーバのディスク使用率が95%を超えたという監視通知があった。
最初に「トップページが見えるのでWebは正常」と結論づけない。静的画面の表示は、注文APIの成功を保証しない。注文APIのHTTPステータスとrequest_idを確認し、Web→APの到達、APのDBエラー、DBの空き容量とログを追う。
原因候補はDBの書き込み不可、APの接続枯渇、アプリの入力エラーなど複数ある。ディスク95%は重要な手掛かりだが、それだけでは根本原因の証明にならない。原因が容量逼迫と確認できた場合でも、データファイルの削除ではなく、承認された容量拡張や不要ファイルの安全な整理などを検討する。復旧後は実際の注文登録と後続処理まで検証する。

## 8. 設計判断：共通基盤と単一障害点
小規模構成ではLB・Web・AP・DBを少数のホストに集約すると費用と管理負荷を抑えられるが、ホスト障害の影響範囲が広がる。大規模構成では役割を分離し、LB、Web/AP、DBを適切に冗長化する。ただし冗長化は障害を完全に消さず、同一電源・同一ストレージ・同一認証基盤などの共通依存が残る場合がある。
設計時は「何が止まると、どの業務が、どの程度止まるか」を依存関係図で確認する。可用性を高めるだけでなく、復旧時間目標（RTO）、許容データ損失（RPO）、費用、運用複雑性を比較する。バックアップは論理的な誤削除や破損への復旧に必要であり、クラスタ構成とは目的が異なる。

## 9. 実務製品との対応
Oracle DatabaseはDBMSの具体例で、インスタンス、データファイル、REDOなどを後続講義で学ぶ。JP1/AJSはバッチ・ジョブの実行順序を管理する例、JP1/IMはイベント集約・監視運用の例、NetBackupはバックアップ管理の例、Citrixは仮想デスクトップ・アプリ配信の例である。ShadowImageやTrueCopyはストレージ複製の例として後続講で扱う。ここでは製品間の一般的な役割を示しており、各製品の個別仕様や対応バージョンは未照合である。

## 10. 要点整理
企業情報システムは入口・業務処理・データだけでなく、DNS・認証・監視・ジョブ・バックアップなどの共通基盤に依存する。構成図では「役割」「配置」「通信」「依存」を分けて読む。正常処理の通過点を把握すると、障害時に最後に成功した境界から原因を絞れる。単一障害点は個々のサーバだけでなく共通サービスにも潜む。
